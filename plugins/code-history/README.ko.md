# code-history

특정 코드가 언제 들어왔고, 어떻게 바뀌었고, 왜 사라졌는지를 git 이력에서 찾아냅니다. 커밋을 나열하는 데서 끝나지 않고 각 변경이 무엇을 노린 것이었는지까지 정리합니다.

## 언제 사용하나요

- 함수나 파일이 지금 모습이 되기까지 어떤 과정을 거쳤는지 알고 싶을 때
- 이 코드를 넣은(또는 바꾼, 지운) 커밋과 PR을 찾아야 할 때
- 왜 이렇게 고쳤는지 배경이 궁금할 때

## 사용법

```
# 함수 이름으로 찾기
/code-history ensure_valid_state

# 코드 패턴으로 찾기
/code-history "user['type'] == 'ADMIN'"

# 파일 경로로 찾기
/code-history src/auth/services.py
```

## 결과물

세 부분으로 나옵니다.

**타임라인 표.** 날짜, 작성자, 커밋, PR, 무엇이 바뀌었는지가 한 줄씩 쌓입니다. 줄마다 변경 유형(추가, 수정, 리팩터링, 이동, 삭제, 복원)과 의도(버그 수정, 기능, 리팩터링, 성능, 정리, 마이그레이션)를 함께 붙입니다.

**상세 분석.** 눈여겨볼 변경마다 이전과 이후를 비교하고, 그렇게 고친 이유와 동작이나 인터페이스가 어떻게 달라졌는지를 짚습니다.

**인사이트.** 코드가 어느 방향으로 흘러왔는지, 그리고 이력에 드러난 문제를 짚습니다. 되돌려진 변경, 같은 자리를 반복해서 손댄 흔적, 커밋 메시지와 실제 diff가 따로 노는 경우 같은 것들입니다. 근거가 이력에 남아 있을 때만 적고, 없으면 적지 않습니다.

## 필요한 것

- `git`
- `gh` CLI (없어도 됩니다. 대신 PR 연결은 커밋 메시지에 적힌 번호에만 의존합니다)

## 알아두면 좋은 점

- 코드를 읽기만 합니다. 어떤 파일도 건드리지 않습니다.
- 관련 커밋이 30개를 넘으면 파일이나 기간으로 범위를 좁힙니다. 어디까지만 살펴봤는지는 결과에 함께 적습니다.
- 한 줄의 작성자만 알면 될 때는 `git blame`이, 커밋 하나만 열어보면 될 때는 `git show`가 빠릅니다. 이 스킬은 변경을 이력 전체에 걸쳐 따라가야 할 때 씁니다.
