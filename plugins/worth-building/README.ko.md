# worth-building

무엇을 어느 수준까지 만들지 정해줍니다. 간단하게 끝낼지 제대로 갖출지 판단하고, 그 수준에 맞는 구체적인 PoC 형태의 제안을 돌려줍니다. 과하지도 부족하지도 않은 크기를 찾는 것이 목적입니다. 나오는 것은 등급이 아니라 바로 시작할 수 있는 제안입니다. 이런 모양으로 만들라, 이건 일부러 뺐다, 이 신호가 보이면 그때 올려라.

## 언제 사용하나요

- 이제 만들려는 것에 얼마나 공을 들일지 저울질할 때. 스크립트든 기능이든 시스템이든 문서든 자동화든 상관없습니다
- "빠르게 갈까 제대로 갈까", "MVP면 될까 진짜 제품으로 갈까", "이거 오버엔지니어링 아닌가", "여기 아키텍처를 얼마나 넣지"
- 애초에 만들 가치가 있는지부터 의심스럽고, 그 답을 감이 아니라 근거로 듣고 싶을 때

소프트웨어에만 쓰는 건 아닙니다. 만들 모양이 이미 정해져 있고 구현만 남았다면 건너뛰어도 됩니다. 이건 크기를 정하는 판단용이지 구현용이 아닙니다.

## 동작 방식

1. **원칙은 하나입니다.** 성립하는 가장 낮은 단계를 기본값으로 잡습니다. 비용이 한쪽으로 기울어 있기 때문입니다. 간단하게 만든 뒤 나중에 덧붙이는 건 쉽지만, 크게 만들어놓고 걷어내는 건 비쌉니다.
2. **위험도를 먼저 봅니다.** 이 판단이 응답의 크기를 정합니다. 되돌리기 쉬운 결정이면 짧은 제안으로 끝내고, 비싸거나 되돌리기 어려운 결정이면 후보를 늘어놓고 비교합니다.
3. **양보할 수 없는 것은 따로 둡니다.** 입력 검증, 데이터 손실 방지, 보안, 기본적인 접근성, 그리고 사용자가 명시적으로 요청한 것. 이것들은 크기를 줄이는 대상이 아닙니다.
4. **모양까지만 말하고 멈춥니다.** 설계로 넘어가지 않습니다. 특정 도구 이름이나 명령어, 단계별 구현 절차는 넣지 않습니다. 그건 다음 일입니다.

## 결과물

위험도가 낮으면 표 없이 짧은 제안이 나옵니다.

> **이 정도면 됩니다:** 만들지 마세요. 시작할 때 환경변수 3개를 읽는 설정 모듈 하나면 충분합니다.
> **왜:** 값 세 개짜리에 시스템이 감당할 만한 복잡도가 없습니다. 계층별 오버라이드나 핫 리로드는 아직 상상입니다.
> **양보 불가:** API 키가 없으면 시작하는 순간 바로 실패하게 합니다. 바깥에서 들어오는 값이기 때문입니다.
> **일부러 뺀 것:** 스키마 검증 라이브러리. 항목이 10개를 넘거나 검증이 반복되기 시작하면 그때 넣으세요.

위험도가 높으면(데이터 마이그레이션, 공개 API, 고객이 직접 쓰는 것) 전체 과정을 밟습니다. 후보 비교표, 권고안, PoC 방향, 일부러 뺀 것 목록, 그리고 언제 한 단계 올릴지 알려주는 신호까지 나옵니다.

## 알아두면 좋은 점

- 맥락이 부족하면 선택 UI 대신 짧은 텍스트 질문으로 되묻습니다. Claude Code 밖에서도 똑같이 쓸 수 있게 하기 위해서입니다. 질문은 두 갈래입니다. 무엇을 만들지 가르는 도메인 사실, 그리고 애초에 만들 필요가 있는지 가리는 질문입니다.
- 질문 때문에 진행이 멈추지는 않습니다. 어떤 가정을 깔았는지 밝힌 잠정 제안과 함께 오기 때문에, 처음부터 답할 필요 없이 틀린 부분만 바로잡으면 됩니다.
- 사용자가 쓰는 언어로 답하고, 말하는 방식에 제안을 맞춥니다.
- 더 충실한 버전을 원한다고 하면 군말 없이 그렇게 만듭니다. 기본값은 기본값이지 규칙이 아닙니다.
